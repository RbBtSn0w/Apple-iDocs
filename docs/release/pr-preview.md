# iDocs pull request previews

iDocs CI still runs its ordinary tests on the PR merge result. After those jobs succeed, **iDocs PR preview package** checks out the full PR head on Apple Silicon, builds the native release archive once, bundles it in an npm tarball, and verifies the tarball in a temporary consumer project. That consumer installs with npm offline and runs the installed `idocs --version`, `idocs --help`, and `idocs resolve --help`. The stable npm installer continues to download the matching native GitHub Release asset.

The run summary and, on same-repository PRs, the bot's Conversation card link to the verified preview. Fork PRs use the Actions summary. The downloadable ZIP expires after 14 days. Its receipt records the PR, full SHA, version, run, packaging job attempt, SHA-256, registry SHA-512 integrity, and bundled native SHA-256. The card and Actions artifact URL also record the immutable artifact ID. Use the card's commands to download, verify, and test an isolated install. The tarball supports macOS 13 or later on Apple Silicon. Use Node.js 22.22.2+ (22.x) or 24.15.0+ (24.x) with npm 12.

The version core is at least the next patch after the stable version actually observed at npmjs. The suffix binds the full head to the PR. If the stable version cannot be verified, Actions still delivers an installable artifact and the publisher refuses it. A later stable release that reaches the preview core blocks any new preview upload for that version.

## Optional registry delivery

After the workflow is available on `main`, a repository maintainer may separately authorize `PR_PREVIEW_PUBLISH_ENABLED=true` and run **Publish iDocs PR preview** on `main` with the iDocs CI run ID and the authorized registry selection. The dispatcher finds the latest successful packaging upload for the current open same-repository PR. A comment-only rerun can increase the run attempt without changing the packaging attempt. The publisher downloads the artifact by ID and validates its receipt and bytes with the workflow's own code. It does not run installed package code or lifecycle scripts and it does not create a GitHub Release or update Homebrew.

- **npmjs** requires a Trusted Publisher connection for `@rbbtsn0w/idocs` with owner `RbBtSn0w`, repository `Apple-iDocs`, workflow `pr-preview-publish.yml`, no environment, and **Allow npm publish**. The job uses npm 12 on a GitHub-hosted runner with `id-token: write`. The separate **Allow npm dist-tag** permission is unnecessary because the workflow only publishes with `--tag next` and reads tags back. Keep the stable `release.yml` connection in place. See [npm Trusted Publishing](https://docs.npmjs.com/trusted-publishers/).
- **GitHub Packages** uses the workflow token with `packages: write`. Give Apple-iDocs Actions write access to the existing package where its settings require it. A reviewer downloading from this registry needs an account with package access and a classic PAT with `read:packages`. See [GitHub Packages authentication](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-npm-registry#authenticating-to-github-packages).

Each selected registry has its own exact-version integrity and `next` observation. A matching existing version is reused without moving the tag. If either registry confirms the archive's exact integrity, its commands appear on the card. The card only reports `next` pointing to that version after reading it back. A later artifact-only run for the same head preserves registry evidence. `next` can move as other previews publish. Use the exact version printed on the card for a particular revision.

For first registry acceptance, a package maintainer authorizes the dispatch. Download the checked artifact, install the exact version in a separate clean Apple Silicon consumer for each selected registry, compare that registry's `dist.integrity` to the receipt, and run the installed entrypoint. Compare the result with the PR Conversation and Actions summaries. Record any unverified registry or tag separately. Do not repack or retry an uncertain upload before checking the exact version and digest.

For local workflow linting, actionlint 1.7.12 predates the Actions `concurrency.queue` option. With that version, use `actionlint -ignore 'unexpected key "queue" for "concurrency" section' .github/workflows/*.yml`. GitHub Actions validates and runs the actual workflow configuration.
